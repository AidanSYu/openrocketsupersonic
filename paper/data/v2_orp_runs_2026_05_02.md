# RFD v2.0 ORP Runs — 2026-05-02

**Status: BLOCKED on .ork motor format**

## Summary

The Super Loki Dart and Arcas `.ork` models built by the prior agent (commit `f8db50ff5`) **do not produce thrust during ORP simulation.** A diagnostic test loaded both files, force-activated the default flight configuration, and ran `Simulation.simulate()`; both produced `hasMotors() == false`, `maxAltitude == 0 m`, `flightTime == 0.0 s`.

## What was attempted

1. Test class: [`core/src/test/java/info/openrocket/core/aerodynamics/SoundingRocketCorpusV2Test.java`](../../core/src/test/java/info/openrocket/core/aerodynamics/SoundingRocketCorpusV2Test.java).
2. Custom Guice setup with `MotorDatabase` bound to an empty `ThrustCurveMotorSetDatabase` (the `.ork` files declare motors inline; the database is queried only as a fallback).
3. Force-activate the rocket's default configuration via `Rocket.setSelectedConfiguration()` and `setAllStages()` before creating the `Simulation`.
4. Set `Simulation.setFlightConfigurationId()` to the active configid in case the constructor defaulted to the empty configuration.

All four steps applied. Result on both vehicles: `hasMotors=false`, `maxAlt=0.000m`, `branches=1`, `flightTime=0.0s`. CSV at `paper/data/csv/v2_orp_runs_2026_05_02.csv` records the diagnostic note verbatim.

## Why the motors don't bind

The `_build_orks.py` script (`paper/data/ork/sounding_rockets/_build_orks.py`) writes a `<motor>` block inside `<motormount>` with `configid` matching the parent `<motorconfiguration>`. That structure looks superficially like the OpenRocket reference fixture (`core/src/test/resources/file/rasaero/export/01.One-stage.ork`), but `OpenRocketDocument.load()` reaches `Configuration.hasMotors()==false` after loading. The reference fixture additionally writes a `<configid>...</configid>` text-content element inside `<simulations>` and may use a different schema for stage activation than the `<stage number="N" active="true"/>` shape the script writes.

Without instrumented logging on the loader's motor-binding path, the exact mismatch is undetermined. The .ork validates as zip + parses as XML cleanly; it just doesn't connect motors to the active configuration.

## Recommendation

1. **Update `_build_orks.py`** to mirror the reference fixture's motorconfiguration / motor / simulation block shape exactly. Specifically:
   - Drop the `<name>` and `<stage>` children from `<motorconfiguration>` (the reference fixture writes empty motorconfiguration tags).
   - Add at least one `<simulation>` block under `<simulations>` with a `<conditions>` and `<configid>` so the loader has a reachable simulation referencing the configid.
2. Re-validate by loading the round-tripped .ork in OpenRocket Swing UI before retesting under JUnit.
3. Once fixed, re-run `SoundingRocketCorpusV2Test`; the test infrastructure (Guice override, force-activate, diagnostic capture) is already in place and committed.

## What this does not block

- The .ork files **are** valid as documentation of the geometry and motor curves — the `<motor>` block contains the digitized thrust-time pairs. They are a useful reference artifact even if our simulator doesn't currently fire them.
- The Arcas wind-tunnel coefficients (`paper/data/csv/arcas_wind_tunnel_combined_2026_05_02.csv`) are independent of the .ork and remain a B-level external static-aero anchor.
- The 27-row v2.0 corpus expansion draft (`paper/data/v2_corpus_expansion_draft_2026_05_02.csv`) keeps its `apogee_thiswork_ft = TODO_pending_orp_run` placeholders. Promotion to `rocket-flight-database/flight_comparison.csv` v2.0 is deferred until the .ork motor binding is fixed.
- All other manuscript closures from this session (Bhagwandin AFF Cmq, Bunescu CFD comparator, MESOS revert to canonical -0.6%, model-mechanism ablation results) are unaffected.
